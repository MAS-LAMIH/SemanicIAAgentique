## Phase 2 — Prepare a minimal evaluator-owned preflight driver

Only if Phase 1 confirms a safe addition-only path, implement a separate preflight driver using existing frozen interfaces.

The driver must:

- Support public D01–D20 single-action tasks and M01–M10 multi-step tasks for visible Providers A and B.
- Support Conditions A, B and C with the same budgets, task inputs, native adjudication and supervision policy.
- Enforce the existing 5-second HTTP request timeout and 60-second outer subject deadline.
- Use the frozen process supervisor, including termination, kill/reap and bounded post-deadline observation.
- Run the reset gate before every attempted execution.
- Reject contaminated initial state before subject launch.
- Use fresh subject processes, fresh trace directories and appropriate fresh registries.
- Preserve runtime traces, native transitions, supervision outcomes, reset evidence and failed attempts.
- Distinguish runtime success, independent native success, safe negative rejection, unsafe mutation, timeout and uncertain late effects.
- Prevent a late mutation after subject termination from being counted as verified success.
- Never introduce automatic retries, compensating actions or implicit planning.

The driver must not change or bypass the frozen runtime or native verifier.

## Phase 3 — Preflight verification matrix

Run a documented A/B-only matrix covering both single-action and multi-step tasks.

At minimum, demonstrate:

### A. Normal execution

- Verified positive single-action task.
- Verified positive two-action chain.
- Verified positive three-action chain.
- Correct negative rejection without forbidden mutation.
- Condition A/B/C parity for supported semantics.

### B. Safety and failure behavior

- FALSE permission causes rejection.
- UNKNOWN permission causes blocking.
- Stale or missing critical evidence cannot authorize mutation.
- HTTP success without native mutation is not verified.
- Incorrect native properties are not verified.
- Forbidden side effects are detected.
- An intermediate chain failure prevents unauthorized continuation.

### C. Timeout and late mutation

- Single-action subject exceeds the outer deadline.
- Multi-step subject exceeds the outer deadline.
- Subject termination and reap are recorded.
- Any subsequent service-side mutation is independently observed when possible.
- Timed-out executions remain unverified even if a desired native state appears later.
- Unsettled state is classified as uncertain, not safe or successful by default.

Use a controlled shorter test deadline where necessary to avoid lengthy fault-injection runs. Preserve the distinction between the shortened test configuration and the proposed 60-second confirmatory deadline.

### D. Reset and isolation

- Clean initial native state permits execution.
- Contaminated initial state is rejected before subject launch.
- Pending requests, permission/revision/call counters and pre-existing records are checked.
- No prior run's trace, registry resolution or native mutation is silently reused.
- Rejected and aborted attempts remain in the evidence inventory.

2. Use fresh output directories.
3. Compare the resulting semantic and native verdicts against the existing frozen public expectations.
4. Record every mismatch, including negative controls and expected diagnostic failures.
5. Preserve the full attempt inventory, not just successful runs.
6. Verify the output completeness and hash inventory.

Expected base coverage is:

- 2 visible providers
- 30 public task families
- 3 conditions
- 1 rehearsal repetition

**Total: 180 planned diagnostic executions**, plus explicitly labeled focused fault-injection probes.

Do not silently substitute a subset for this full rehearsal. If resource constraints prevent completion, report partial coverage and the reason.

These are diagnostic executions, not independent provider samples or confirmatory evidence.

## Stop conditions

Stop and report rather than silently repair if:

- A frozen generic implementation change is required.
- A native-oracle or semantic contradiction is discovered.
- The combined driver cannot safely supervise single-action tasks.
- A reset contamination is not detected or is incorrectly cleared.
- A timeout is incorrectly reported as verified success.
- The new driver introduces condition-specific advantages.
- Any Provider C material would need to be accessed.

If a genuine defect is discovered, preserve the failure and propose a separately reviewed change-control procedure. Do not patch the frozen baseline in place.
