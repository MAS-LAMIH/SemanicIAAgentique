 1. Scientific positioning and claim boundaries
 The starting work describes Agent & Artifact environments, Web of Things descriptions, and semantic Usage
 manuals with operations, preconditions, and postconditions. Semantic service discovery, mediation,
 substitution, and goal-oriented composition have extensive prior art. Likewise, LLM planning, symbolic
 verification, and feedback-driven repair are not claimed as new.

 Potential contribution: A controlled empirical account of the total cost, correctness, and limits of reusing
 semantic capability knowledge across independently authored Web API providers, plus a secondary test of
 what LLM-assisted planning contributes beyond classical planning.

 Excluded claims: (i) RDF is intrinsically more reliable than JSON; (ii) ontology mediation is newly invented; (iii)
 an LLM is necessarily superior to classical planning; (iv) an HTTP success response proves a goal; (v) scripted
 API tests establish sustained real-world use.

 Research questions

   Question                    Frozen wording / role


   RQ1 - Primary               To what extent does reusable ontology-mediated capability knowledge reduce total and incremental
                               effort for integrating independently developed Web APIs while preserving correct execution?


   RQ2 - Secondary             Given identical formal goals and integrated services, when does LLM-assisted planning and repair
                               improve over classical semantic planning?


   RQ3 - Exploratory           How accurately does an LLM formalize ambiguous natural-language requests and request clarification
                               when needed? May be deferred.




 2. Hybrid architecture and independence rules
 Hybrid model: Provider A, B, and held-out C each have independently maintained capability manuals. A shared
 registry exposes common ontology concepts, mapping assertions, and discovery endpoints. Generic validation,
 planning interfaces, and execution adapters use these descriptions at runtime.

  • Provider manual: locally named operations; input/output schemas; critical preconditions; modeled transitions
    and effects; API bindings; evidence/observation requirements; documentation provenance.

  • Shared registry: provider/manual discovery, shared vocabulary, versioned reusable mappings, and provenance
    of mappings. It must not encode task-specific plans or a direct A-to-B substitution table.

  • LLM: candidate plan proposals, interpretation of feedback, and optional goal formalization. The LLM is not the
    authority for action validity.

  • Symbolic layer: capability mediation, precondition evaluation, candidate filtering, transition reasoning, and
    structured violation evidence.

  • Executor: HTTP invocation, explicit observation/read-after-write, and audit trace. Declared and observed
    effects are logged separately.

 Authoring independence: Authors may see the common vocabulary and agreed manual schema, but not
 held-out tasks, oracle answers, or target mappings. Record who authored each manual, examples available,
 and all central mapping intervention.


 3. Formal contract and operational semantics
 An operation is a = (I, P, T, B, O), where I is its input schema/constraints; P its critical state preconditions;
 T(s,s′) its modeled transition relation; B its concrete API binding; and O its observation/evidence specification.
 A goal G consists of required state predicates and mandatory invariants.

 Applicability, progress, achievement and verification
  • Applicability: Applicable(a,s,x) iff input x satisfies I and every critical precondition in P is established true from
    admissible state evidence.

  • Three-valued evidence: preconditions are true, false, or unknown. Unknown critical facts require observation,
    clarification, or rejection; missing RDF facts are never treated as true.

  • Progress: at least one modeled successor can advance an outstanding subgoal without violating invariants.
    Progress does not imply complete goal achievement.

  • Achievement: observed post-execution state s′ satisfies all goal predicates and invariants.

  • Verification: O specifies fresh and sufficient evidence to support the achievement claim. An HTTP 2xx alone is
    insufficient.

 Substitution and repair
 A replacement b is considered only if it is applicable in the current state, its input/output transformations are
 explicitly available, and its modeled transitions support the outstanding goal. Distinguish existential feasibility
 (some modeled outcome succeeds) from conservative preservation (all relevant successful modeled outcomes
 meet the obligation). Neither guarantees real-world API behavior.

 Repair feedback records: action, constraint identifier, verdict (false/unknown), observed facts, evidence
 source, and proposed next step. Repaired plans are checked again before execution.

 Parity requirement: B and C receive the same capability meanings, constraints, effects, mappings,
 transformations, observations and validation power. Audit functional parity before any performance
 comparison. A-to-(B/C) isolates shared semantic infrastructure; B-to-C isolates RDF-native implementation
 choices, not semantic knowledge availability.

 E2 classical/LLM fairness
 Use identical formal goals and observations. Allow the classical planner to replan after state changes; use the
 same execution budget and validation feedback. Record invalid proposals separately from invalid executed
 actions. E3, if undertaken, uses an independent oracle allowing multiple acceptable interpretations and
 mandatory clarification cases.


 5. Providers, held-out integration, and leakage prevention
 Pilot domain: three calendar-like providers with independently authored documentation and manuals. A and B
 are visible for initial integration; C is sealed until the generic system is frozen. Weather and public-holiday APIs
 may supply context but should not dominate E1.


   Provider                     Designed challenge


   A - initial                  Conventional create/update/read operations; baseline integration.


   B - initial                  Different names, parameters, output formats and capability vocabulary; positive cross-provider
                                mappings.


   C - held out                 Unseen interface with positive and negative matches: misleadingly similar operation names,
                                non-equivalent effects, restricted permissions, missing evidence or unsupported transitions.


 Procedure: (1) independently author A/B manuals; (2) independently prepare and seal C plus evaluation
 tasks/oracle; (3) freeze generic discovery, validator, planner interfaces, prompts and registry logic; (4) reveal
 C; (5) permit only C-specific manuals, bindings and mappings; (6) log all changes and failures; (7) test both
 safe rejection and verified execution.

 6. Complete cost accounting and break-even analysis
 C_total(n) = C_setup + sum(i=1..n) C_onboard(i) + C_maintenance(n). Cost is measured from a declared
 starting point, not only after the shared ontology exists.


   Cost category                   Included work


   Setup                           Ontology/vocabulary design; common mapping curation; shared registry; validator and reusable
                                   mediation implementation; adaptation of tutorial agent; initial tests.


   Onboarding per provider         Reading documentation; authoring manuals/contracts; new mappings; input/output adapters;
                                   provider-specific rules; tests; failed attempts; debugging.


   Maintenance                     API revisions; repair of mappings/manuals; validator updates; regression tests; documentation
                                   updates.


 Measurement record: elapsed person-minutes; integrator identity and experience; edited files/artifacts;
 mapping assertions added/reused; rules; lines changed; tests; failures; debugging; tool/LLM assistance;
 correctness at completion. If only one integrator is available, disclose the limitation.

 Cold start, incremental reuse, and amortization
  • Cold start: all study-specific infrastructure and initial provider work are charged to the condition.

  • Incremental: onboarding held-out C after A/B are integrated; distinguish reused knowledge from newly
    authored alignments.

  • Break-even: plot observed cumulative costs for n = 1, 2, 3. If no crossing occurs, report no observed
    break-even. Any extrapolated crossing is explicitly a model-based sensitivity estimate with assumptions about
    future provider mix, mapping reuse, labor cost and maintenance.

 Interpretation: A faster marginal integration does not prove lower cumulative cost. The study must report both
 and may find that semantic infrastructure remains more expensive across the observed sample.


 7. Correctness oracle and negative controls
 Before running systems, independently specify per-task required end-state predicates, forbidden side effects,
 acceptable alternatives, and observation requirements. Use fixture-controlled API responses and
 read-after-write or state queries for writable services.

  • Count false-positive substitutions, false-negative rejections, valid call execution, verified end-state
    achievement, and unknown-state handling separately.

  • Include deceptive labels, different operations with equivalent effects, operations with similar labels but
    incompatible effects, missing permissions, missing evidence and service failures.

  • A condition is counted as successfully integrated only if required tasks are achieved or safely rejected as
    appropriate. Unsafe execution is a failure even when HTTP returns success.

 8. Sampling, statistical analysis, and limits
 Begin with 20 diagnostic pilot cases covering valid actions, multi-step goals, failures, semantic mismatch, and
 invalid substitutions. These cases validate the apparatus; they do not support strong generalization. Extend to
 more held-out providers, independent manual authors and integrators if feasible.

 Provider is the primary unit of generalization for onboarding cost. Repeated LLM runs on the same
 provider/task are not independent provider samples. Publish raw task-level results, paired differences,
 uncertainty intervals, failure taxonomy and protocol deviations. Predefine retry limits, timeout, repair iteration
 budget and human-intervention rules before confirmatory runs.

 9. Go / no-go decision procedure

 Gate 1 - Readiness (required before confirmatory E1)
 Executable contract semantics; independent manuals; sealed held-out C and tasks; verified B/C parity; frozen
 generic machinery; complete cost logs; negative substitution cases; independent observable oracle. If any is
 missing, continue engineering but do not label runs confirmatory.

 Gate 2 - Evidence (direction-neutral)
 Report correctness and cumulative/marginal costs regardless of sign. Accept that reuse may improve, worsen,
 or leave outcomes indistinguishable. A negative result does not trigger selective metric changes or unreported
 redesign.

 Gate 3 - Research Track decision
 Proceed only if the final study supports a differentiated, generalizable empirical finding, with full-text
 comparison to classical semantic service mediation and recent neuro-symbolic agent work. If evidence
 remains a small scripted prototype, prefer demo/resource positioning over inflated research claims.

 10. Implementation boundary and staged plan
 Reuse target: adapt the referenced Agentic AI tutorial for LLM invocation, tool calling and agent execution
 loop, subject to an implementation/license audit. No verified mapping of tutorial classes/modules is claimed
 here. Do not rebuild a full multi-agent framework.

 Minimal vertical slice: one independent manual, one formal goal, one executable API contract, one applicability
 decision, one API call, one observed postcondition, and one evidence-backed explanation. Then integrate
 provider B, freeze generic code, and test held-out C.

 Suggested stack, not frozen dependencies: Python agent runtime (tutorial adaptation); RDFLib/SPARQL; SHACL
 or narrow procedural checks for constraints; HTTPX/FastAPI for controlled services; JSON logs plus optional RDF
 provenance. Tool choices may change without altering the experimental protocol, provided costs are logged.

 11. Known unresolved choices (must be recorded, not silently
 assumed)
  • Exact contract ontology IRIs, SHACL shapes, and supported transition-language fragment.

  • Concrete API implementations and how provider authors/integrators are assigned independently.

  • Frozen retry budget, timeouts, task distribution, mapping policy, and numerical success thresholds.

  • Whether sufficient providers/integrators can be recruited for a generalizable full-paper evaluation.

  • Whether any real operational deployment exists; public API invocation alone does not establish In-Use
    maturity.
