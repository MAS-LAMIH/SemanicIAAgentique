Provider author, curator, integrator, independent reviewer and approver should be
separate qualified people. If the curator also curates manuals, native truth still
requires independent review against source service semantics rather than trusting those
manuals. The same exposed implementation author/AI collaborator is not an independent
reviewer or blind integrator. AI/tool sessions inherit the exposure of materials they
receive; “a different chat” is not proof of organizational independence.

## Custody stages (proposed; none authorizes access now)

1. Assign named custodian/reviewer/author/integrator/approver and declare all prior
   exposure, authorship, institutional/financial interests and assistance. Unknown prior
   dates stay null with an explicit unknown declaration. Do not infer unexposed status
   from a repository search or the absence of a recorded access event.
2. Retain sealed provider and task/oracle materials outside this workspace/public Git
   history with least-privilege access. Publish only approved nonrevealing custody IDs,
   version digests, custodianship and sealing timestamps. Do not copy secret values,
   interface examples or task answers into logs. Integrity hashes support audit but do
   not prove service independence or prevent earlier off-platform exposure.
3. Before contributor release, obtain independent reviews and register the task-instance
   manifest, feasibility/predicate schema, observer procedure, actual schedule/roster,
   cost policy, allowed additions and exact candidate/review hashes. Custodian confirms
   custody without this assistant examining sealed content.
4. Investigator signs a distinct scientific freeze decision and then, if appropriate,
   a separate release authorization specifying participants, exact artifact classes,
   hashes, time window and allowed use. No gate is auto-approved by passing tests.
5. Custodian stages only the authorized provider documentation/API access to integrators.
   Expected answers/native reader code remain segregated. Curator/reviewer may access
   authoritative native semantics to prepare approved observation bindings without
   redefining frozen goal truth. Audit every read/write and output transfer.
6. Archive additions/diffs, dependency/import review, costs and source hashes before and
   after runs. Preserve failures, unsupported positives and uncertain state. No automatic
   widening of permissions or reuse of expected answers as subject mappings.

No Provider C-specific material or task answer is produced as part of these stages here.

## Exposure log and conflict handling (proposed)

Use an append-only exposure log separate from the resource ledger. Each actual event
records: event ID; participant/role/session IDs; artifact class and custody identifier;
SHA-256/version; first-access UTC timestamp; purpose; authorizing decision ID; actual
channel and recipients (including AI/tools); permitted use; earlier external-exposure
statement; conflict declaration/disposition; reviewer and linked corrections. Log task
inputs, mappings, expected answers, native reader code, raw outputs and feedback as
well as provider documentation. Redact secrets without hiding semantic failures.
An empty template is not an observed access history. No fictitious exposure events or
signatures are created here.

Independent reviewer signs an exposure/conflict statement and the exact review findings,
not just a role title. If staffing forces overlap, declare it before access and obtain
a written investigator disposition, second external review where feasible, tighter
access limits and explicit claim restrictions. Unresolved conflicts block release.
If an implementer/integrator already knows intended holdout data or answers, replace
the contaminated material under an approved genuinely new-holdout design or label
that run exploratory. Counterbalancing or approval cannot retroactively restore blinding.
Public A/B tasks/answers stay disclosed as public, even under a new provider interface.

## Allowed integration/change boundary (proposed)

Only approved provider-local additions are allowed after release: manuals/contracts,
declarative API bindings/transform compositions supported by frozen primitives,
provider-local semantic mappings, tests/fixture/runtime configuration and independently
reviewed native observation bindings through frozen `NativeInterpretation` /
`ChainInterpretation` interfaces. Proposed path allowlist follows the existing
[held-out protocol](HELD_OUT_EVALUATION_PROTOCOL.md); the investigator must lock exact
paths/contributors before release. No such directory/material is created here.

Path names alone are insufficient: auditor must reject monkey-patches, unchecked
mutation paths, hidden answers, oracle overrides, new generic transform primitives or
task-specific repairs placed inside an ostensibly provider-local directory. The public
A/B-only diagnostic runners are not promised to support a new provider directly; an
approved provider-local evaluation driver must use frozen interfaces and equal rules.
External services beyond the loopback transport are unsupported under this candidate.

Generic resolver, validation/evidence semantics, shared meanings/interfaces/prompts,
execution/sequence/supervisor logic, goal/oracle truth, cost collector and frozen task
family logic cannot change after unsealing while retaining the original confirmatory
baseline. Genuine core defects stop affected runs; preserve evidence/costs, obtain
independent classification and report failure under baseline or retire it for a newly
reviewed candidate. Same exposed-provider repaired runs are exploratory unless a
prospectively valid uncontaminated restart is available.
